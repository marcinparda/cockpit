Implement GitHub issue `$ARGUMENTS` end to end, ending on an open PR carrying its own review. The issue closes itself when the PR merges.

Tracker operations use the `gh` CLI (`docs/agents/issue-tracker.md`). Where a GitHub MCP server is connected, its issue and PR tools do the same job; `gh` is the default.

## 1. Read the issue

`gh issue view <n> --comments`. A bare number or a title: resolve a title with `gh issue list --search`. The latest **Agent Brief** comment is the spec; the body alone is not. Stop and report back if the issue is `needs-info`, `ready-for-human`, or `wontfix`.

Done when the acceptance criteria are listed and each maps to a seam you can test.

## 2. Branch

```
git switch master && git pull --ff-only && git status --short
```

The working tree must be clean; report anything dirty and wait. Then branch off `master` as `<prefix>/<n>-<kebab-title>`, with prefix `feature/`, `bugfix/`, `refactor/` or `docs/` by the issue's category: `bugfix/162-habits-period-picker-flaky-test`.

## 3. Build

Use /tdd at pre-agreed seams: confirm the seams with the user before the first test. Run typechecking regularly, single test files regularly, lint before finishing, and the full suite once at the end. Read the relevant `AGENTS.md` and `docs/standards/` for the area first.

Commit to the branch in conventional-commit style (`fix(habits): ...`), one logical change per commit.

## 4. Docs

Walk `docs/AGENTS.md` and update every doc whose subject the diff touches (`docs/projects/`, `docs/backend/`, `docs/standards/`, `CONTEXT.md`, ADRs). Update in the same branch as the code.

Done when each changed behaviour is either reflected in a doc or consciously needs none.

## 5. Write the implementation review

Write it before the PR exists, to `<scratchpad>/pr-body.md`, from the diff and the Agent Brief. It becomes the PR body, in this order:

1. `## Summary`: one or two lines, then `Closes #<n>` on its own line.
2. `## Implementation review`: one bullet per acceptance criterion, ticked against the brief, each naming the files and the seam that proves it. Then the decisions taken and their trade-offs, anything the brief left open, any deviation from the brief, and what stays out of scope.
3. `## Using simpler words`: the same change explained for a learner. Plain language, every term of art defined on first use, one concrete example with real values from this change (a before/after, or a walk through one input), and an everyday analogy where one fits. It adds understanding the review above lacks; it does not repeat the review shorter.
4. `## Test plan`: the commands run and their results.

End the body with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.

Done when every acceptance criterion has a bullet that cites a file, and the simpler-words example uses values from this diff.

## 6. Push and open the PR

```
git push -u origin HEAD
gh pr create --base master --title "<conventional title>" --body-file <scratchpad>/pr-body.md
```

Merge closes the issue through `Closes #<n>`; closing by hand is never needed.

## 7. Check the review with /code-review

Run /code-review with fixed point `origin/master`, spec source issue `<n>`, and the implementation review as a second spec source: every claim it makes is checked against the diff. When a claim is wrong or missing, fix the implementation review and update the PR with `gh pr edit <pr> --body-file <scratchpad>/pr-body.md`.

Post the output on the PR, keeping the two axes apart:

- **Summary comment**: the `## Standards` and `## Spec` reports plus the one-line summary, via `gh pr comment <pr> --body-file <file>`.
- **Inline comments**: every finding tied to a file and line goes in one review, via `gh api repos/{owner}/{repo}/pulls/<pr>/reviews` with `event: COMMENT` and a `comments` array of `{path, line, side: "RIGHT", body}`. A finding without a line stays in the summary comment.

Begin every posted comment with `> *This review was generated by AI.*`.

Done when the summary comment is visible on the PR (`gh pr view <pr> --comments`), every inline finding appears in its review, and every implementation-review claim the review flagged is corrected in the PR body.

## 8. Report

Give the user the issue link, the PR link, the branch, the test result, and the review's worst finding per axis. Merging is theirs.
